## 一、问题背景（这个项目为什么存在）

工厂和机房里的设备——伺服驱动器、BMS、变频器——各自说着不同的"语言"（CAN、I2C、UART），数据是孤岛，运维靠人跑现场，故障往往等设备停摆了才发现。**网关这个产品品类干的就是这件事**：把各种设备的数据统一采集、解包、诊断、上云，实现远程监控、告警和固件升级。有人物联网、映翰通、四信都在做这个形态，这是一个真实的工业产品品类，不是学习玩具。

## 二、需求分析

**功能需求**
- 上行采集：CAN 总线周期数据（转速/温度/母线电压，100ms）、故障码与告警（1s）
- 下行控制：远程指令下发，**必须有执行确认**——远程控制不能开环
- 诊断：按 ISO-14229（UDS）思路实现会话控制、按标识符读参数、读故障码
- 本地监控：OLED 实时显示，含掉线状态
- 远程监控（增强项）：MQTT 上报 + 断线重连

**非功能需求（这才是工程师和调参党的分界）**
- 实时性：端到端时延目标 1~3ms（Week2 实测填数）
- 可靠性：设备掉线 3~5 个周期内检出；IWDG 看门狗兜底；总线错误帧监控
- 可观测性：队列丢弃、总线负载、错误帧计数——**丢没丢帧、负载高不高，系统自己知道**
- 可维护性：OTA 最小版（Bootloader 跳转 + 有效性标志）

## 三、方案设计

**三层架构**：下位设备层（第二块 C8T6 模拟）/ 网关层（STM32F103 + FreeRTOS，核心）/ 云平台层（MQTT + 看板，增强）。

**关键设计决策（每条都要能讲出"为什么"）**

| 决策 | 理由 |
|---|---|
| 帧 ID 分段：0x1XX 周期数据 / 0x2XX 事件 / 0x3XX 控制 / 0x5XX 诊断 | ID 越小仲裁优先级越高——周期数据实时性最强，总线拥塞时先抢到总线 |
| 控制闭环：0x300 下行 + 0x301 确认 + 200ms 超时告警 | 开环控制等于"发完就信"，执行没执行你不知道 |
| 掉线阈值 3~5 个周期 | 误报与检测延迟的权衡，不是拍脑袋 |
| 接收放中断、解包放任务 | 中断里只做搬运，重活不放中断——中断越短，系统响应越稳 |
| 任务优先级按速率单调 + 实时性分级 | CAN 接收是系统输入源头，优先级最高；显示/监控可延迟 |
| 位时序：500kbps、BRP=4、18TQ、采样点 77.8% | 采样点偏后是为补偿传播延迟和时钟偏差（能手推 500k 和 250k 两组） |

## 四、实现路径

模块化契约先行：15 个模块每个都有**接口签名 + 约束 + 验收标准**（见 `Device_Monitor_Modules.md`），写完一个烧录验证一个再开下一个。四周节奏：W1 工程模板 + bxCAN + loopback → W2 解包 + 掉线检测 + 台架互通 → W3 诊断服务 + 监控屏 → W4 OTA 最小版 + README + 投递。每周有总闸门，不过不进下周。

## 五、完整性体现在哪（被问"你这项目完整吗"时的答案）

- **全链路**：设备 → 网关 → 云，数据走通过去，指令走得回来
- **双向**：上行采集 + 下行控制闭环（带确认），不是只能看的单向系统
- **故障域覆盖**：掉线检测、诊断否定响应、看门狗、错误帧监控——**坏的情况都设计过了**
- **工程闭环**：设计文档 → 模块契约 → 实现 → 验收 → README → 简历投递，每一步有产出

一句话：**完整性不在功能多，在每个设计决策有理由、每种故障有处理。**

## 六、后续改进设想（roadmap，面试主动讲"我知道边界在哪"）

- OTA 完整版：双分区 + CRC 校验 + 失败回滚（四步流程能讲）
- J1939 解析（29 位扩展帧 + PGN/SPN 信号组织）
- 多节点扩展（一台网关带多个设备，ID 管理策略）
- 断网补传（本地缓存 + 重连后补发）
- 完整 Web 看板（实时曲线 + 控制按钮）
- 车载场景映射（口头讲）：AUTOSAR 分层、网络管理 NM、ASIL、车规器件——"迁到车载的增量在这些，协议层和架构层我已经有了"
