## 〇、项目定位：一套系统，三层架构

### 系统组成

| 层       | 组件                          | 技术栈                     |
| ------- | --------------------------- | ----------------------- |
| 下位设备层   | 伺服驱动器 / BMS（台架用第二块 C8T6 模拟） | CAN · I2C · UART        |
| 网关层（核心） | STM32F103C8T6 + FreeRTOS    | 采集 · 解包 · 诊断 · 上报 · OTA |
| 云平台层    | MQTT Broker + Web 看板        | 远程监控 · 远程控制             |

**产品故事**：工厂/机房里的设备各自说着不同的"语言"（CAN、I2C、UART），数据孤岛、运维靠人跑现场。网关把它们统一采集、解包、诊断、上云，实现远程监控、告警和固件升级——这是真实的工业网关产品品类（有人物联网、映翰通、四信等都在做这个形态），不是一个" 学习玩具"。

### 为什么包装成通用系统（而不是车载网关）

1. **叙事姿态**："我做了个车载网关" = 面试官一眼看出对着 JD 做项目，深挖"你测过实车吗"就露怯；"我做设备数据采集与远程监控系统，CAN 是我接入的工业设备总线之一" = 展示系统设计能力，车载映射变成口头加分项
2. **一个项目打三片市场**：车企（CAN/UDS/RTOS）、工业 IoT（MQTT/OTA）、物联网云——README 调侧重即可，不用维护双版本简历
3. **台架更成立**：两板对话在工业语境下是标准演示环境；CAN 在工业界本来就有（伺服、BMS、光伏逆变器、工程机械 J1939），故事零编造成分

**诚实的边界**（面试防御线）：简历和 README 只写真实实现——通用系统；车载对应关系是口头讲的迁移能力，不冒充车载/实车经验。被问到"没上车怎么懂车载"时，答案就是下面那张映射表。

### ⚠️ CAN 引脚避坑（CubeM配置时）

F103 的 CAN1 **默认引脚 PA11(RX)/PA12(TX) 与小蓝板 USB 的 D-/D+ 冲突**。CubeMX 里把 CAN 引脚**重映射到 PB8(RX)/PB9(TX)**，物理上远离 USB 信号。一分钟的设置，避开一个能调半天的玄学故障。

### 台架架构

```
┌────────────────┐  CAN 总线（双绞线，两端各 120Ω）  ┌────────────────┐
│  模拟下位设备  │ ───────────────────────────────▶ │   边缘网关     │
│  C8T6+TJA1050  │  0x100 设备数据 100ms            │ C8T6+TJA1050  │
│  （第二块新板）│  0x200 故障码/告警 1s             │                │
└────────────────┘  0x300/0x301 控制指令+确认        └────────────────┘
                     0x500/0x501 诊断请求/响应              │ OLED 本地显示
                                                           │（增强）ESP8266 → MQTT → Web 看板
        ┌────────────────┐
        │ USB-CAN 分析仪 │ ◀── 挂在总线上：PC 发诊断请求 / 抓包 / 看负载
        └────────────────┘
```

- 总线两端各 120Ω 终端电阻（TJA1050 模块板通常自带，**到手先万用表量**，没有就并一个）
- 波特率 **500 kbps**（工业 CANopen 主流，车载同值）
- 面试讲点：**为什么 CAN 用差分双线**——抗共模干扰，车间/车内电磁环境恶劣

### CAN 帧设计（v2 完整表，DBC 思路）

| 报文        | ID    | DLC | 周期    | 方向     | 信号布局                                                                                                              |
| --------- | ----- | --- | ----- | ------ | ----------------------------------------------------------------------------------------------------------------- |
| MotorData | 0x100 | 8   | 100ms | 设备→网关  | byte0-1 转速 uint16（1rpm/LSB）· byte2-3 控制器温度 int16（0.1℃/LSB）· byte4-5 母线电压 uint16（0.1V/LSB）· byte6 工作状态 · byte7 校验和 |
| AlarmDTC  | 0x200 | 8   | 1s    | 设备→网关  | byte0-2 故障码（3 字节）· byte3 告警状态位 · byte4-7 运行时间戳                                                                    |
| CtrlCmd   | 0x300 | 1   | 事件    | 网关→设备  | byte0 命令字（0x01 启动 / 0x02 停机 / 0x03 故障复位）                                                                          |
| CtrlAck   | 0x301 | 4   | 事件    | 设备→网关  | byte0 回显命令字 · byte1 执行结果 · byte2-3 指令序号                                                                           |
| DiagReq   | 0x500 | 8   | 请求-响应 | 诊断仪→网关 | 诊断请求（0x22/0x19 等服务）                                                                                               |
| DiagResp  | 0x501 | 8   | 请求-响应 | 网关→诊断仪 | 肯定响应 / 0x7F 否定响应                                                                                                  |

设计说明（每条都是面试讲点）：

- **ID 分段策略**：0x1XX 周期数据 / 0x2XX 事件告警 / 0x3XX 控制下行 / 0x5XX 诊断。**ID 越小仲裁优先级越高**——0x100 周期数据实时性最强所以 ID 最小，总线拥塞时先抢到总线。被问"ID 怎么分配的"时，这是设计出来的答案
- **控制闭环**：0x300 下行必须有 0x301 确认，网关侧 200ms 未收到 ack 报"指令超时"。远程控制不能开环——"你怎么知道指令被执行了？"
- 上表按 **Intel（小端）字节序**定义，要讲得出和 Motorola 的区别——"信号跨字节怎么拼"是面试常问
- 0x300 演示**下行链路**：Web 看板/本地按键发指令 → 网关转发 → 模拟设备执行并回确认——远程控制完整闭环
- **时间戳说明**：无 RTC，时间戳 = 设备上电运行时间；上云后可由 Broker/SNTP 对时（roadmap）
- **J1939**：29 位扩展 ID + PGN/SPN 组织信号，与乘用车 CAN 同族。本计划用 11 位标准帧 + 自定义信号表；J1939 解析写入 roadmap，PGN/SPN 概念能讲即可

### 模拟设备侧需求清单（第二块板，Week2 前完成）

台架节点用第二块新 C8T6 + CubeMX 生成（不用改 mcu_os 老工程，同套 CubeMX 工程改配置即可，预计 100 行内）：

- 定时器 100ms 发 0x100、1s 发 0x200（轮询发送，查邮箱状态，别阻塞主循环）
- **接收 0x300 → 执行 → 回 0x301**（控制闭环的设备侧）
- 开机自检时自动发一次 0x22 诊断请求（顺便当"自己的诊断仪"，Week3 演示用）
- Week3 起诊断主请求方切换为 USB-CAN 分析仪（PC 端现成工具），mcu_os 侧保留开机序列即可

### 位时序配置（面试高频，必须能手推）

APB1 = 36MHz，目标波特率 500 kbps：

- 预分频 BRP = 4 → TQ 时钟 = 36M/4 = **9 MHz**，每格 111ns
- 每位需 9M/500k = **18 TQ**
- 分段：SYNC 1 + BS1 13 + BS2 4 = 18 TQ
- **采样点 = (1+13)/18 ≈ 77.8%**（常用区间 75%~87.5%）
- SJW = 4 TQ（再同步补偿上限，不能超过较短段）

讲点：采样点为什么不在 50%（补偿传播延迟和时钟偏差）；各节点波特率偏差为什么必须控制在窄范围。

**必做练习**：把波特率改成 250kbps（BRP 仍 4）重推一遍——位宽、TQ 数、BS1/BS2 全变。**位时序没有唯一正确组合**，BRP 不同、切分不同，能自圆其说就行；面试时讲得出"我这组数的理由"比背参数重要。

## 二、软件架构设计

### 任务划分（6 个任务，含设计理由）

| 任务              | 触发方式     | 优先级    | 职责                                            |
| --------------- | -------- | ------ | --------------------------------------------- |
| can_rx          | 中断投递     | **最高** | HAL_CAN 接收中断 → 帧入队；中断里只做搬运，重活不放中断             |
| can_parse       | 队列驱动     | 高      | 按信号表解包 → 更新共享数据区（互斥量保护）；**维护每个 ID 的"最后接收时刻"** |
| diag_srv        | 事件驱动     | 高      | 设备诊断服务（参照 ISO-14229）：会话控制 / 读参数 / 读故障码 → 响应帧  |
| net_report（增强项） | 队列驱动     | 中      | ESP8266 AT 状态机 + MQTT 上报 + 断线重连               |
| display         | 周期 200ms | 低      | OLED 监控屏（转速/温度/电压/告警/**掉线状态**）                |
| health          | 周期 1s    | 最低     | 栈余量、堆余量、总线三件套计数、任务存活检查、喂 IWDG                 |

优先级原则：**速率单调 + 实时性分级**——CAN 接收是系统输入源头，优先级最高；诊断是请求-响应式，时效敏感；显示/监控可延迟。这张表本身就是面试讲点。

### 设备掉线检测（v2 新增，核心功能）

- can_parse 更新每个设备 ID 的"最后接收时刻"；health 每秒检查，**超过 3~5 个周期未更新 → 判定掉线** → OLED 显示离线 + 上报告警
- 讲点："工业网关的核心价值不是数据上云，是**设备掉线你知道**。你怎么发现掉线的？阈值怎么定？"（3~5 个周期 = 误报与检测延迟的权衡）
- **演示爆点**：拔掉 CAN 线 → OLED 和 Web 看板同步变"离线" → 插回恢复。这个 demo 比"数据在上飘"有说服力十倍，进 10 分钟脱稿稿

### 任务间通信矩阵

| 机制   | 用在哪                                    | 讲点                    |
| ---- | -------------------------------------- | --------------------- |
| 队列   | can_rx → can_parse 帧缓冲（深度 8~16，按突发流量算） | 深度怎么定；满了丢帧还是覆盖（带计数上报） |
| 互斥量  | 共享数据区、OLED、CAN 发送                      | 优先级继承；故意演示一次翻转再修复     |
| 事件组  | 诊断会话激活、网络上线/离线                         | 多事件等待，替代标志位满天飞        |
| 任务通知 | can_parse 唤醒 display 立即刷新              | 比队列轻量，讲清适用场景          |

### 数据流

```
模拟设备 --CAN 0x100/0x200--> can_rx(中断) --队列--> can_parse --互斥量--> 共享数据区
                                                              ├─▶ display --> OLED
                                                              └─▶ net_report --> ESP8266 --> MQTT --> Web 看板
诊断仪(PC/分析仪) --CAN 0x500--> can_rx --队列--> diag_srv --CAN 0x501--> 响应
Web 看板下发 --MQTT--> net_report --CAN 0x300--> 模拟设备 --CAN 0x301--> 确认（闭环）
掉线判定 --health--> display/OLED + 告警上报
```

### 可观测性与健壮性设计（v2 新增）

| 项        | 实现                                                    | 成本         |
| -------- | ----------------------------------------------------- | ---------- |
| 总线三件套    | 队列丢弃计数、总线负载率（帧/s ÷ 理论峰值）、错误帧/BusOff 计数 → OLED 一页 + 串口 | 几十行        |
| 任务级监控    | 各任务周期性更新自己的"存活标记"，health 检查到标记不动就报出具体哪个任务卡死           | 几十行        |
| IWDG 看门狗 | CubeMX 勾选 + health 喂狗，任务监控定位 + 看门狗兜底恢复的二级防护           | CubeMX 级别  |
| S3 会话超时  | 0x10 扩展会话激活后 **5 秒**无诊断活动自动回默认会话（UDS 规定的 S3server）    | 一个定时器 + 事件 |

讲点："你怎么知道总线负载高？""丢帧了你怎么发现？""会话怎么管理的，超时谁负责？"——这些都是从概念级变实现级的深挖点。

## 四、4 周冲刺计划（11/17 – 12/14，每天 8h 强度）

> 前提：示波器焊板并行会挤占时间。若 12 月中只完成 CAN + 诊断 + 本地监控（无 MQTT），**也足够投递**。

### Week 1（11/17–11/23）· 工程模板 + bxCAN 基础 + 位时序

- CubeMX 建工程：HAL + FreeRTOS（Native 接口、Heap4、堆 8KB、SysTick 1ms 时基、Timebase 源改 TIM4、Debug 选 Serial Wire）；**CAN 引脚重映射 PB8/PB9**（避开 PA11/12 USB 冲突）
- Day 1 收尾（待办）：3 个 include 挪进 `USER CODE BEGIN Includes` 块；Keil 勾 `Use MicroLIB`；F7 编译 0 错误 → F8 烧录
- **Day 1 验收**：PC13 每 500ms 闪 + 串口每秒一行 `[mon] ...`，**heap_free 在 5000~5500 之间**
- Day 1 收尾后做**抢占实验**：Task_Mon 加 100ms 忙等，优先级 1（低于 LED）灯照常闪；改成 4（高于 LED）灯明显变慢——双向对比，抢占式调度亲眼见过
- bxCAN 初始化：按第一节位时序参数填；先用 **loopback 自发自收**模式，不接线验证寄存器配置
- 位时序：能手推 500k 全参数 + **完成 250k 变体练习**（BRP=4，一位几个 TQ、BS1/BS2 怎么切）
- 对照临界区实现，理解 FreeRTOS 任务级/中断级临界区的差异
- 下单：2×小蓝板 + 2×TJA1050 + OLED + USB-CAN 分析仪
- 验收：串口打印自发热帧；讲得出位时序每个参数各管什么

### Week 2（11/24–11/30）· 中断接收 + 解包 + 掉线检测 + 台架点亮

- TJA1050 到手：两节点接线，先做**物理层回环验证**（A 发 B 收，确认总线真的通）
- HAL_CAN 接收中断（Rx0 FIFO 中断）+ 帧入队
- **验收滤波**：只收 0x100/0x200/0x300/0x301，其余滤掉——配 32 位标识符屏蔽寄存器，串口对比滤波前后中断频率
- can_parse 任务：按信号表解包 → 共享数据区（互斥量）
- 模拟设备侧代码（第二块板）：按第一节需求清单实现
- **掉线检测**：最后接收时刻维护 + health 超时判定 + OLED 掉线显示
- **控制闭环**：0x300 下行 + 0x301 确认 + 200ms 超时告警
- **端到端时延实测**：模拟设备发 0x100 时翻转 GPIO-A，网关解析完成翻转 GPIO-B，示波器测边沿间隔（预期 1~3ms）——简历"端到端时延 XX ms"的数字来源
- 验收：网关串口实时打印转速/温度/电压，与设定值一致；OLED 点亮；**拔线看掉线演示**；讲得出"为什么接收放中断、解包放任务"

### Week 3（12/1–12/7）· 设备诊断 + 监控屏收尾

- 诊断服务 0x10 会话控制（默认 ↔ 扩展）→ 0x22 按标识符读（设备型号/固件版本）→ 0x19 读故障码
- 否定响应 0x7F + NRC 码（服务不支持、会话未激活等）
- **S3 会话超时**：扩展会话 5s 无活动自动回默认会话
- ISO-TP 概念：单帧/首帧/连续帧——流程图要能画
- OLED 监控界面：转速大字 + 温度/电压条 + 告警图标 + **掉线状态**
- USB-CAN 分析仪上岗：PC 端发 0x22 请求、抓总线帧存日志（README 素材）
- 下行控制闭环联调：Web/本地发 0x300 → 设备执行并回 0x301
- 验收：分析仪发 0x22 → 网关回正确设备信息；发不存在的标识符 → 回正确的否定响应；**能画出一次完整诊断的时序图**

### Week 4（12/8–12/14）· 增强项 + 沉淀 + 投递启动


按优先级从上到下，时间不够就砍下边的：

3. MQTT 增强项（前三周顺利才做）：ESP-01S + AT 状态机 + JSON 上报，照 `IoT_Terminal_Plan.md` 阶段 2 现成方案
4. Web 看板（可选，一天）：Spring Boot + 网页，实时曲线 + 控制按钮
- README：系统框图、任务表、通信矩阵、CAN 帧表、**故障场景 demo（拔线→掉线→恢复）**、遇到的问题及解决过程、**"量产车载网关你会改什么"FAQ**（车规器件/AUTOSAR 分层/NM/ASIL/DBC/多路 CAN）

## 五、CAN/诊断学习要点清单（附面试预埋问题）

### CAN 必须搞懂

| 知识点 | 深度要求 | 面试预埋问题 |
|---|---|---|
| 帧格式：标准/扩展帧、数据/遥控帧 | 能逐字段画一帧 | "一帧 CAN 数据部分最多几字节？"（8） |
| 仲裁机制 | 懂逐位仲裁、ID 越小优先级越高 | "两节点同时发帧会怎样？输的那方怎么办？"（自动重发） |
| 位填充 | 懂规则、懂为什么 | "为什么要位填充？"（同步+纠错） |
| 错误帧 + 错误计数器 | 懂 TEC/REC、主动/被动、BUSOFF | "节点什么时候 BUSOFF？进了怎么恢复？" |
| ACK 应答 | 懂没有应答 = 没人收 | "怎么知道帧发出去了但没人收？" |
| 位时序 / 采样点 | **能手推**（500k 和 250k 两组） | "500kbps、36MHz 时钟，位时序怎么配？采样点为什么偏后？" |
| 验收滤波 | 会配 + 懂为什么 | "总线负载高时怎么降低 MCU 中断频率？" |
| bxCAN 双 FIFO / 中断 | 懂两个接收 FIFO 的用法 | "FIFO 满了会怎样？怎么防丢帧？" |
| 错误帧现象识别 | 用 USB-CAN 分析仪亲眼见过 | "位时序配错总线上是什么现象？"（错误帧暴涨） |

### 诊断服务必须搞懂（协议参照 ISO-14229，即 UDS 同一标准）

| 知识点 | 深度要求 | 面试预埋问题 |
|---|---|---|
| 诊断分层：应用层 + 网络层（ISO-TP） | 概念清晰 | "诊断报文和普通 CAN 报文什么关系？" |
| 0x10 会话控制 | 默认/编程/扩展会话差异 + **S3 超时** | "为什么有些服务要先切会话？会话超时谁负责？" |
| 0x22 按标识符读 | DID 定义、响应格式 | "DTC 和 DID 有什么区别？" |
| 0x19 读故障码 | 状态位含义 | "故障码怎么存储、怎么按状态位过滤？" |
| 0x7F 否定响应 | 常见 NRC 码 | "服务不支持时回什么？" |
| ISO-TP 单帧/多帧 | 流程图能画 | "超过 8 字节的诊断数据怎么传？" |
| 0x27 安全访问 | 概念级 + 简化实现 | "写服务怎么防止被恶意调用？" |

> ISO-14229 就是车载 UDS 依据的标准，工业设备诊断同样用它——"诊断协议我按 UDS 实现过"这句话在两种语境下都成立，不是包装话术。

### 顺带能聊的（概念级，不深究）

- **AUTOSAR CP 分层**：MCAL / 基础软件层 / 服务层 / 应用层——"网关里诊断栈跑在哪一层"
- **ISO 26262**：ASIL 等级概念——"车身网关通常要求什么 ASIL"
- **网络管理 NM**：休眠唤醒协调机制（呼应砍掉的低功耗项）
- **J1939**：PGN/SPN 信号组织方式——商用车/工程机械场景
